# Contract: Plan Selection, Order and OAuth Continuation

**Status**: Planned behavior; [technical plan](../plan.md), [tasks](../tasks.md) and [physical interface](storage-operations.md) are drafted, not implemented. [Entitlement interface](entitlements.md) and [access client flow](../../002-authentication-api-access/contracts/client-onboarding.md) and [Node.js onboarding](../../002-authentication-api-access/contracts/onboarding-workflow.md) must be implemented together without moving billing into MCP.

HTTP routes and browser/server handoffs are fixed in the access [endpoint contract](../../002-authentication-api-access/contracts/endpoints.md); payment rules remain authoritative here.

## Surface and trusted invocation

Billing owns plan-selection/order/activation content and Stripe operations in its separate Lambda. Access coordinator renders/proxies that browser flow using a bounded verified-identity continuation and CSRF protection; it invokes only the exact billing alias via IAM. Purchase-only enrollment requires no paid MCP token; management requires current paid eligibility under [access FR-004](../../002-authentication-api-access/spec.md#functional-requirements), including existing links/sessions. No directly callable billing function URL is allowed. Spec 002 owns explicit REST ingress wiring; Stripe's dedicated webhook goes directly to billing and is signature verified, never forwarded to MCP.

Implement billing as an isolated Node.js ES-module package with its own npm lockfile, Express app and REST-v1 Lambda proxy adapter, following the [runtime plan](../../002-authentication-api-access/plan.md). Dispatch IAM-invoked internal operations directly to billing services; only REST HTTP events enter Express. Register the Stripe webhook with `express.raw({ type: 'application/json' })` before JSON middleware, preserving exact bytes through base64 decoding in the Lambda adapter. Verify with the official Stripe Node SDK before mutation; test signed plain/base64 events and reject tampered bodies. [Stripe's Express example](https://github.com/stripe/stripe-node/blob/master/examples/webhook-signing/express/main.ts) documents raw-body middleware ordering.

Logical internal operations: list approved plans; create/reuse own-account order and Stripe Checkout session; inspect own order/activation state; open own management portal only while paid-eligible, with per-operation eligibility enforcement or guarded management operations if hosted sessions cannot provide it; reconcile own order against Stripe when an authorized access request or billing queue/replay invokes a bounded check. Request context contains verified identity pair, opaque access-issued continuation reference, environment, correlation/idempotency reference and a selected catalog plan/duration/version when applicable. The browser can choose a plan and one of its configured durations but cannot supply trusted identity, Stripe customer, arbitrary price, redirect destination or successful status. Physical payloads/table conditions follow the storage-operation contract; secret handling follows the billing plan.

The versioned Parameter Store [shared catalog](plan-catalog.md) is authoritative for sellable plan details and usage-plan mappings; listing and Checkout use its bounded cache and quote-version checks. Only approved plan→one-time Stripe price mappings are accepted, with explicit test/live environment, currency/service_term and operator-provided product/price IDs. No price or quantity can be forged via client input. Explicit paid upgrades use the [immutable server-quoted net amount](plan-upgrade.md) instead of the full base offer price. Store order identity, chosen plan/duration/price/service-term/environment, customer/subscription/session linkage, attempts/state and committed entitlement revision. Return the approved Stripe Checkout URL transiently to the same bound session; keep it out of logs/evidence. Bind provider session metadata through an opaque order reference; do not send OAuth state, verifier, refresh/access tokens or raw identity claims to Stripe.

Checkout creation also persists reconciliation work and schedules the delayed billing check before handing the Checkout URL back to access; queue-send failure remains recoverable from durable work. Delay, Pipe delivery, retries and confirmed-payment no-op behavior are authoritative in the [delivery contract](../../002-authentication-api-access/contracts/background-delivery.md#delayed-reconciliation-and-retries).

## State and completion

`plan_selected → order_created → checkout_open → payment_pending → paid_committed` with explicit cancelled/failed/retryable outcomes. A verified webhook or server-side reconciliation can establish trusted payment only under the configured subscription policy. Checkout completion alone is insufficient for unpaid/asynchronous sessions. Validate environment/order/customer/subscription association and payment state; commit order/subscription/event/projection and durable decision history before reporting payment activation. Access status/resume requests re-read current entitlement and conditionally advance matching live transactions; billing cannot mutate access-owned state. Browser success parameters only request a status refresh.

The trusted response to access is own-order state plus current entitlement plan/validity/revision or a pending/denied reason, never an access token or native API key. Access additionally waits for its matching ready subscriber usage-plan binding, then returns an OAuth code to the AI host and issues tokens at code exchange. Billing cannot redirect a bearer token to the AI host or sign a Cognito token.

Repeated/concurrent checkout requests for the same intended order reuse the durable result and provider idempotency mapping. Inspect existing eligible subscription or pending order before creating another; explicit plan changes are a separate intentional action. An untrusted order ID, expired/other-user continuation or changed session identity cannot fetch/update another account. Persisted pending states and bounded billing reconciliation and request-driven native-key retries handle webhook/key-propagation delays without duplicate charges or fail-open access.

Cancel/failure shows an actionable own-account result. OAuth expiry/abandoned browser does not reverse a committed payment or force repurchase. Fresh identity verification checks current entitlement before completing application login; old continuations cannot mint codes. Redirects after Checkout/portal return only to exact configured access onboarding endpoints with opaque references. Distinguish provider delivery delay from committed billing state and access-owned metering readiness.

## Policy inputs and acceptance

Prices/tiers/intervals, active/trial/grace/cancellation eligibility, refunds/disputes and retention remain billing-policy inputs; initial active-paid/no-grace assumption stays explicit. Do not conflate subscription expiry, JWT TTL and native plan quota period.

Local fixtures must exercise first purchase, active reconnect, cancelled/failed/delayed payment, duplicate initiation/event, concurrent/reordered events, cross-user continuation, arbitrary price, server restart, Stripe/storage failure, payment after OAuth expiry and pending native activation. Demonstrate zero duplicate effects and no access grant from browser return. Real Stripe account changes/charges/webhook registration and host sign-in remain unperformed.

[Stripe Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment), [subscription webhooks](https://docs.stripe.com/billing/subscriptions/webhooks). These support server-verified fulfillment; the coordinator/continuation boundary is this project's planned architecture.

## Callback and reconciliation handoff

Access persists pending state between short browser requests. Billing verifies webhook or reconciliation, commits entitlement and decision history; browser status/resume consistently reads entitlement and performs bounded provisioning. Webhook cannot redirect the user; no activation queue or background access completion is required. Billing SQS/replay recovers missing payment events without a browser. Access binding leases recover only on subsequent valid requests; late payment is reused on fresh authorization without reviving expired OAuth. The [delivery contract](../../002-authentication-api-access/contracts/background-delivery.md) owns billing-only queue/replay details.

First purchase and renewal use one-time Checkout payment mode under [manual renewal](manual-renewal.md); no Stripe automatic renewal. Cancellation requests for current terms use verified support tickets, not a self-service renewal toggle.

No self-service active-term downgrade, cancellation or refund is offered. Management pages display the configured support email; backend operations enforce the same restriction even if a request bypasses UI. Zero/excess upgrade credits also go to support without Checkout or entitlement mutation. Expired users may select an available plan as a new manual purchase, not a modification/refund of an active term.
