# Contract: Plan Selection, Order and OAuth Continuation

**Status**: Requested behavior, pending spec 003 technical plan/tasks. [Entitlement interface](entitlements.md) and [access client flow](../../002-authentication-api-access/contracts/client-onboarding.md) and [Node.js onboarding](../../002-authentication-api-access/contracts/onboarding-workflow.md) must be implemented together without moving billing into MCP.

## Surface and trusted invocation

Billing owns plan-selection/order/activation content and Stripe operations in its separate Lambda. Access coordinator renders/proxies that browser flow using a bounded verified-identity continuation and CSRF protection; it invokes only the exact billing alias via IAM. Purchase-only enrollment requires no paid MCP token; management requires current paid eligibility under [access FR-004](../../002-authentication-api-access/spec.md#functional-requirements), including existing links/sessions. No directly callable billing function URL is allowed. Spec 002 owns explicit REST ingress wiring; Stripe's dedicated webhook goes directly to billing and is signature verified, never forwarded to MCP.

Implement billing as an isolated Node.js ES-module package with its own npm lockfile, Express app and REST-v1 Lambda proxy adapter, following the [runtime plan](../../002-authentication-api-access/plan.md). Dispatch IAM-invoked internal operations directly to billing services; only REST HTTP events enter Express. Register the Stripe webhook with `express.raw({ type: 'application/json' })` before JSON middleware, preserving exact bytes through base64 decoding in the Lambda adapter. Verify with the official Stripe Node SDK before mutation; test signed plain/base64 events and reject tampered bodies. [Stripe's Express example](https://github.com/stripe/stripe-node/blob/master/examples/webhook-signing/express/main.ts) documents raw-body middleware ordering.

Logical internal operations: list approved plans; create/reuse own-account order and Stripe Checkout session; inspect own order/activation state; open own management portal only while paid-eligible, with per-operation eligibility enforcement or guarded management operations if hosted sessions cannot provide it; reconcile own order against Stripe when the access recovery handler requests a bounded check. Request context contains verified identity pair, opaque access-issued continuation reference, environment, correlation/idempotency reference and a selected catalog plan when applicable. The browser can choose a plan but cannot supply trusted identity, Stripe customer, arbitrary price, redirect destination or successful status. Physical payloads, tables/conditions and secret delivery are spec 003 planning obligations.

Only approved plan→Stripe price mappings are accepted, with explicit test/live environment, currency/interval and operator-provided product/price IDs. No price or quantity can be forged via client input. Store order identity, chosen plan/price/environment, customer/subscription/session linkage, attempts/state and committed entitlement revision. Return the approved Stripe Checkout URL transiently to the same bound session; keep it out of logs/evidence. Bind provider session metadata through an opaque order reference; do not send OAuth state, verifier, refresh/access tokens or raw identity claims to Stripe.

## State and completion

`plan_selected → order_created → checkout_open → payment_pending → paid_committed` with explicit cancelled/failed/retryable outcomes. A verified webhook or server-side reconciliation can establish trusted payment only under the configured subscription policy. Checkout completion alone is insufficient for unpaid/asynchronous sessions. Validate environment/order/customer/subscription association and payment state; commit order/subscription/event/projection and a durable activation notification before reporting payment activation. Access consumes the committed notification through a scoped outbox-stream handler, re-reads current entitlement and conditionally advances matching live transactions; billing cannot mutate access-owned state. Browser success parameters only request a status refresh.

The trusted response to access is own-order state plus current entitlement plan/validity/revision or a pending/denied reason, never an access token or native API key. Access additionally waits for its matching ready subscriber usage-plan binding, then returns an OAuth code to the AI host and issues tokens at code exchange. Billing cannot redirect a bearer token to the AI host or sign a Cognito token.

Repeated/concurrent checkout requests for the same intended order reuse the durable result and provider idempotency mapping. Inspect existing eligible subscription or pending order before creating another; explicit plan changes are a separate intentional action. An untrusted order ID, expired/other-user continuation or changed session identity cannot fetch/update another account. Persisted pending states and bounded scheduled billing reconciliation/native-key retries handle webhook/key-propagation delays without duplicate charges or fail-open access.

Cancel/failure shows an actionable own-account result. OAuth expiry/abandoned browser does not reverse a committed payment or force repurchase. Fresh identity verification checks current entitlement before completing application login; old continuations cannot mint codes. Redirects after Checkout/portal return only to exact configured access onboarding endpoints with opaque references. Distinguish provider delivery delay from committed billing state and access-owned metering readiness.

## Policy inputs and acceptance

Prices/tiers/intervals, active/trial/grace/cancellation eligibility, refunds/disputes and retention remain billing-policy inputs; initial active-paid/no-grace assumption stays explicit. Do not conflate subscription expiry, JWT TTL and native plan quota period.

Local fixtures must exercise first purchase, active reconnect, cancelled/failed/delayed payment, duplicate initiation/event, concurrent/reordered events, cross-user continuation, arbitrary price, server restart, Stripe/storage failure, payment after OAuth expiry and pending native activation. Demonstrate zero duplicate effects and no access grant from browser return. Real Stripe account changes/charges/webhook registration and host sign-in remain unperformed.

[Stripe Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment), [subscription webhooks](https://docs.stripe.com/billing/subscriptions/webhooks). These support server-verified fulfillment; the coordinator/continuation boundary is this project's planned architecture.

## Callback and reconciliation handoff

Access persists pending state between invocations; billing operations return promptly. Signed webhook → committed own-order/entitlement/outbox → access Node.js event handler → conditional state transition after current-state recheck is the activation path. Browser polling reads its own access status at bounded intervals. Early notifications, crashes and missed stream delivery recover through durable outbox reads and scheduled own-order reconciliation; linking an order always rechecks current entitlement. Billing can complete payment after OAuth expiry without reviving that transaction. Finalize physical outbox keys, transactions, due-work/read indexes, retention and provider-query idempotency in spec 003 before access integration.
