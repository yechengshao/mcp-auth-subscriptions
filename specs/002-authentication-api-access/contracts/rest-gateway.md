# Contract: REST API and Native Subscriber Usage Plans

**Status**: User-confirmed target, pending implementation. The existing `infra/lambda/runtime.yaml` and verifier/report v1 remain the legacy HTTP API profile. HTTP API IDs, `$default`, route IDs and payload 2.0 are not the REST target.

HTTP routes/methods and browser handoffs follow the [endpoint contract](endpoints.md). Discovery aliases and stage/domain routing follow the [client contract](client-onboarding.md#discovery-and-host-compatibility).

## REST surface and ownership

Spec 002 owns `AWS::ApiGateway::RestApi`, resources, methods, AWS_PROXY integrations, REQUEST authorizer/binding/permission, deployments, explicit named stage, sanitized logs, GatewayResponses, native usage plans and all REST backend-alias invocation permissions. Spec 001's planned `infra/lambda/runtime-rest.yaml` supplies the MCP function/version/live alias/log group and native provider environment; it creates no gateway resource or invoke grant. Spec 003 owns billing Lambda/storage/business logic and its outputs; the gateway assembles the dedicated REST ingress, including a Stripe-signature-verified billing webhook targeting the exact billing alias. No HTTP-API import helper is needed for this migration.

Expose a canonical `https://<rest-api-id>.execute-api.<region>.amazonaws.com/<stage>/mcp` and protected `/health`. Paid methods use CUSTOM plus ApiKeyRequired; MCP uses `ANY` to preserve service 405 handling, health uses GET. Authentication/OAuth discovery/metadata, coordinator routes and the Stripe webhook are explicit separate methods without a paid API-key gate; each uses its own protocol/session/signature validation. No catch-all unauthenticated integration to MCP. No Function URL, alternate-stage permission or broad method wildcard bypass. Protect aliases with exact SourceAccount and API/stage/method/path SourceArn.

REST integration uses Lambda proxy event **v1**, invocation POST and a **29000-ms** integration timeout; retain service timeout default 25 seconds and current buffered JSON constraints. Do not carry HTTP API payload-format-version or AutoDeploy fields into REST IaC. Explicit deployments must change/redeploy when methods/integrations change; stage references a completed deployment. Verify event path/stage, query, repeated/multivalue headers and base64/body behavior through the packaged pinned adapter. Preserve canonical `/mcp` without a redirect. REST trailing-slash behavior must be measured: there is no invented empty-path-segment resource for `/mcp/`. Local service slash normalization remains; document the REST edge result and prove it cannot bypass paid authorization. If a base-path adapter setting is needed, bind it to tests rather than stripping the stage blindly.

## WAF and baseline protection

API Gateway does not enable AWS WAF by default. This plan does not provision a WAF web ACL or associate one with the REST stage; do not claim WAF protection from REST API creation, the custom authorizer or usage plans. AWS Shield Standard provides baseline DDoS protection automatically, but does not supply WAF request-filtering rules. Public discovery/OAuth/onboarding/webhook methods have no subscriber usage-plan gate and must not be described as protected by per-subscriber limits.

Enabling WAF requires an explicit infrastructure decision: a regional AWS WAFv2 web ACL, rules and an association with the named REST API stage in the same region, with additional WAF charges. Review rules against OAuth callbacks, token requests, MCP payloads and signed webhooks before enforcement; validate the deployed association and allowed/blocked behavior separately from authentication and metering. No WAF provisioning or live validation is claimed here.

## Native metering

The REST API uses `ApiKeySourceType=AUTHORIZER`. Each paid method requires a key. After service JWT signature/claim/expiry validation without datastore reads, the authorizer returns the signed native key **value** claim as top-level `usageIdentifierKey`; API Gateway handles its plan lookup/metering. It does not inject an `x-api-key` header. The AI client only needs its bearer access token.

Access owns one stable native key per subscriber/environment and maps each approved `plan_id` to a native UsagePlan associated with the paid REST stage. A subscriber's key can belong to only one plan for that stage. Same-tier subscribers have separate keys, not a shared tier key. Keep key mappings in access-owned storage; the signed access JWT deliberately exposes the key value to its holder. Never place it in callback URLs, Stripe metadata, public infrastructure outputs or logs. The authorizer copies the validated claim; it cannot read bindings, create or move keys. AUTHORIZER source prevents a raw key header from bypassing token authorization.

A separate access provisioning/reconciliation path creates or reuses a subscriber key and associates the selected plan idempotently, recording current entitlement revision, API/stage/plan and readiness. Recheck revision around asynchronous work; stale workers cannot mark old-tier binding ready. Plan changes transition through pending/denied while the old association is removed and the new one is established; preserve subscriber identity and document native usage-counter behavior rather than promising a reset or exact transfer. API Gateway association propagation may take minutes: missing association/throttle/mapping errors remain pending or fail closed, never unmetered fallback. Subsequent issuance/refresh requires the current ready mapping. Existing access tokens retain their signed key until expiry under the [revocation bounds](authorization.md#denial-and-revocation); gateway association/plan changes may independently affect outstanding requests.

Rates/bursts/quotas and tier-to-native-plan IDs are explicit inputs, no invented pricing. Native usage plans meter gateway requests per key; they do not count successful tools or Stripe invoice units. Quotas/throttles are best effort and can be exceeded; strict paid credits/cost caps need another design. Observe 429 behavior separately from entitlement 403 and authentication 401. Do not claim exact quota cutoff in local or live acceptance.

## Discovery and unauthorized responses

Configure REST UNAUTHORIZED and invalid-token paths to return 401 plus an exact advertised `WWW-Authenticate` resource_metadata URL. Authorization denial is 403; gateway configuration errors remain errors. Explicit public metadata routes target the access coordinator, not MCP. Named-stage paths and path issuer discovery must resolve at their advertised locations; test each host's discovery before cutover. No hidden custom-domain dependency.

## Migration and deployment order

1. Bootstrap service ECR/publishing IAM and billing storage independently. Create the access-owned base REST API without methods/deployment/stage to learn its API ID and predictable stage URLs. Do not create an empty API deployment.
2. Configure retained Cognito create/reuse and coordinator callback/issuer/resource URLs using that identity; deploy access state/signing/functions. Deploy the service-only runtime using the REST host, and deploy the billing processor with storage/identity inputs. Alias outputs exist before their integrations.
3. Update gateway wiring with exact service/access/billing aliases, authorizer, public metadata/onboarding/webhook methods, protected paid methods and tier plans; create a deployment only after methods exist, then its named stage and plan-stage associations. No runtime output depends on an already deployed stage, so provisioning stays acyclic.
4. Locally verify REST contracts and retain live status as not_run. When authorized prerequisites exist, validate end-to-end host OAuth, payment/activation, code exchange, actual REST transport/denial/metering and rollback before changing client configurations.
5. Reconfigure host MCP resource/connection and grant audience to the new stage-prefixed URL. Existing HTTP API ID/URL remains distinct and retained. Any continued legacy endpoint must enforce the same paid gate or be disabled through a separately scoped cutover action; it cannot remain an unguarded paid-service bypass. Old grants are not silently audience-rewritten. Rollback restores an explicitly secured endpoint/configuration; no automatic deletion or identity reset.
