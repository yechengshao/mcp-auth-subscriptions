# Contract: Shared Browser Session Mechanism

**Status**: Confirmed simple session strategy; implementation/live validation pending. One cookie format, one server-side schema/store and the same expiration policy serve onboarding and subscription management. No extra table, function, long-lived management token, ChatGPT-token handoff or session-refresh endpoint.

## Issuer, storage and expiry

Cognito verifies identity; the access Lambda creates the application session. Use Node crypto to generate at least 32 random bytes, encode as opaque base64url, store only SHA-256(token) in the SESSION key and send the raw value only in a Secure, HttpOnly cookie. Cookie name is deployment-specific and fixed by server configuration; Path must cover the access routes, omit Domain where practical, and validate SameSite behavior against Cognito/Stripe top-level callbacks (default Lax, no cross-site mutation exemption). Never place this session token in URLs, logs, localStorage or MCP JWTs. HTTPS protects transport; possession of a session cookie does not override workflow-stage/ownership checks.

A session record in AccessState contains purpose=onboarding|management, authentication_stage=pending_identity|identity_verified, tx_id, optional verified identity/subscriber_id only after Cognito validation, CSRF digest, revision, created_at, expires_at and delete_after. Session token and CSRF token are independently random. Use one generic TX record schema with purpose discriminator: onboarding requires validated AI-client/redirect/resource/PKCE fields; management instead permits only a fixed local destination and MUST NOT invent downstream OAuth fields or issue MCP credentials. Upstream state/nonce/PKCE attempts use the same correlation/validation machinery for either purpose.

All browser sessions and their pending login context expire absolutely at start+1800 seconds. No sliding extension, refresh token or twenty-four-hour management cap is added. Rotating after identity verification preserves the original deadline and invalidates the pre-login cookie/session atomically; issue fresh CSRF material. Cookie lifetime never exceeds remaining server expiry. Check expiry before TTL deletion; disposable cleanup rules follow access storage. Session existence alone never means paid application login.

## Login and management entry

OAuth onboarding continues to start at `/authorize` and follows the existing callback/code flow. Direct subscription management starts at GET `/billing`: a valid verified session can render only the own-account management allowed by current paid eligibility; otherwise redirect to GET `/login`. That endpoint starts a management-purpose transaction and redirects to Cognito using its own upstream state/nonce/PKCE. It accepts no arbitrary return URL or AI callback override. This is shared session/login code, not a separate identity provider or credential format.

The common Cognito callback validates the saved purpose/session/attempt and tokens, rotates the session, binds verified identity, then routes onboarding to `/onboarding` and management to the fixed `/billing` page. An active Cognito/identity-provider browser session may avoid another credential prompt, but that is not guaranteed. An ineligible user cannot browse billing records or upgrade; show subscription-required/reconnect or support guidance without disclosure. Mere possession of an old MCP token is not a browser management session.

Recheck current eligibility/ownership on every management operation, including a still-valid session; paid expiry/revocation blocks operations immediately under existing rules. An expired session never self-renews from its cookie: GET pages start Cognito reauthentication; mutation requests return a noncacheable 401 session_expired with a fixed local login action and perform no effects. Do not redirect/replay a payment POST automatically. After new verification create a new session and ask the user to deliberately retry any mutation under normal idempotency guards. No duplicate charge/key/credit effect.

## Shared protection and scope

Pre-identity sessions can only advance the original login. Verified onboarding sessions can select/purchase and inspect their own bounded order; verified sessions may manage their own subscription only while currently paid. Purpose routes completion but is never authority by itself. Validate CSRF on browser mutations, origin as appropriate, session-to-transaction identity, absolute deadline and ownership; do not derive identity from browser-supplied references. Disabled portal/downgrade/cancel/refund flows remain support-only.

Express sets/parses cookies; select a maintained compatible session adapter or small explicit handler implementation during implementation. Its behavior must match hash-only DynamoDB storage, per-record TTL, expiry and atomic rotation; express-session MemoryStore or Lambda process memory cannot be authoritative. No raw token logging or storing whole provider tokens as session identity shortcuts. Logout invalidates the current session, clears its cookie and revokes an associated application refresh family only when that session actually owns one; a direct-management session need not have an MCP refresh family.

T014/T015/T018 define/test both purpose schemas, secure cookie settings, pending→verified rotation, session fixation rejection, CSRF/ownership, already-verified reuse, expired-session reauthentication, closed-browser return, ineligible paid management denial, mutation retry without replay and no MCP-token/browser leakage. Live Cognito/client cookies remain separate acceptance; no deployed session behavior is claimed.
