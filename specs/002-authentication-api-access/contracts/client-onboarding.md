# Contract: AI Client Connection and Paid OAuth Completion

**Status**: Behavioral contract; local client/OAuth/onboarding simulations are in progress, with live ChatGPT/Claude and AWS acceptance not run. Applies to the REST target profile; [Node.js onboarding](onboarding-workflow.md), [authorization](authorization.md), [gateway](rest-gateway.md) and [billing continuation](../../003-billing-subscriptions/contracts/checkout-onboarding.md) define the trust boundaries.

HTTP methods, route names and browser/server handoffs are defined in the [endpoint contract](endpoints.md).

## Browser and client sequence

1. ChatGPT/Claude connect/sign-in/first protected request initiates authorization when the host chooses. Installation alone is not a portable redirect hook. Missing/invalid bearer access receives an upstream 401 with `WWW-Authenticate: Bearer resource_metadata="<advertised HTTPS metadata URL>"`. The resource metadata identifies the exact canonical MCP resource and access-coordinator issuer.
2. The host sends the coordinator `/authorize` a registered client ID, exact redirect URI, state, approved scopes, MCP `resource`, `response_type=code`, S256 challenge and method. Validate before any redirect. Persist a bounded DynamoDB transaction and respond promptly with the login redirect. The browser sees only an opaque reference; progress survives Lambda restarts. Initial clients are explicitly registered with `token_endpoint_auth_method=none`; do not advertise CIMD, DCR, private_key_jwt or OIDC userinfo until implemented and tested. Exact ChatGPT callback/client configuration comes from its management page; Claude configuration is independent.
3. The coordinator redirects to Cognito identity verification using its own upstream authorization-code/S256 transaction. Its Cognito callback is distinct from the AI-client callback. Validate upstream state/nonce/PKCE and Cognito tokens, then durably bind immutable Cognito issuer/subject to the pending downstream transaction and conditionally advance its persisted onboarding state using current entitlement. Never pass an upstream Cognito code to the AI host.
4. With a trusted bounded identity continuation, read current entitlement; this is not successful application login. Eligible subscribers always skip purchase: a matching ready binding permits completion, otherwise status/resume performs bounded key/association setup without creating another order. Only users without eligible paid entitlement see spec 003's approved plan selection, order and Stripe-hosted Checkout through the billing-owned flow. The coordinator supplies identity via a scoped internal IAM call, not a browser-supplied subject or a paid MCP bearer. Purchase/status actions return via the coordinator with browser CSRF protection; management operations enforce [FR-004](../spec.md#functional-requirements). Stripe sees only the billing order's scoped identifiers, not OAuth state/PKCE or client credentials.
5. Browser Checkout return displays pending/success/cancelled state through short status requests. Billing commits verified entitlement and decision history; access status/resume requests read current entitlement and advance matching transactions; a browser return cannot establish payment. Transition logic and resume endpoint require server-side verification: committed current billing entitlement plus matching ready subscriber usage-plan binding. Payment-confirmed-but-binding-pending remains activation pending; no access code/token yet. Successful AWS configuration and conditional persistence mark the binding ready without a propagation probe; failed/uncertain AWS setup returns a retryable user-facing activation error (or configuration error with support guidance), with idempotent recovery on a later request under the REST gateway contract. Stripe redirect parameters are never payment authority.
6. After a conditional transition marks OAuth completion ready and the browser resume endpoint confirms the transaction is still valid, return a short-lived one-use code, original state and exact issuer `iss` to the registered AI callback. Errors to a previously validated redirect include state and matching issuer too. An invalid/unregistered redirect is a local error, never a redirect. No access/refresh token, usage key or subscription record enters the callback URL.
7. At `/token`, verify the code atomically once, client, exact redirect, original S256 verifier and resource. Recheck entitlement and ready binding before issuing access/refresh tokens in a noncacheable JSON response. The host stores them and sends `Authorization: Bearer <access_token>` on subsequent MCP requests. The resource audience matches the canonical `/mcp` URL exactly.
8. At the same `/token` endpoint, `grant_type=refresh_token` rotates the opaque refresh credential, checks grant/client/resource binding and current paid entitlement/binding, rejects replay and enforces grant expiry/revocation. Eligible reconnect and refresh never create new Stripe orders. Expired users reopen the same identity-verification/plan-selection/one-time-payment onboarding flow; there is no automatic Stripe renewal. Unpaid users may reopen only purchase/renewal enrollment; paid application login, refresh and billing management remain denied.

Browser management uses the [same session mechanism](browser-sessions.md) and Cognito callback, with fixed local completion rather than an AI OAuth code.

## Durable state and bounds

The [Node.js onboarding contract](onboarding-workflow.md) implements these phases with conditional DynamoDB writes, durable provisioning state and request-driven retries, with billing-only background payment recovery; browser/session and code/grant storage remain authoritative across retries. No gateway request or Lambda worker remains open for the waiting phases.

Persisted transaction phases are `pending_identity → identity_verified → checkout_pending → payment_pending → code_ready → code_issued → redeemed`; a current paid subscriber may skip checkout, and `activation_pending` belongs to the subscriber binding rather than the transaction. A Cognito cancellation before identity verification persists terminal `cancelled`; terminal `failed`, expired, cancelled, or redeemed transactions cannot mint codes. Payment may finish after the OAuth transaction expires: preserve the paid subscription, require fresh authorization and reuse that entitlement instead of charging again.

Technical defaults to implement and test: authorization continuation 30 minutes absolute, authorization code 60 seconds one-use, token lifetimes and refresh deadline/rotation as defined in [authorization](authorization.md#denial-and-revocation). Browser sessions are bounded to the onboarding transaction and use Secure/HttpOnly/SameSite cookies, login-session rotation and anti-CSRF for mutations. Expiry is checked on every use; DynamoDB TTL deletion is only housekeeping. Concurrent/replayed transitions use conditional/transactional writes. Store digests of codes/refresh credentials, not their raw values; exclude state, codes, cookies and verifiers from logs. Binding records store native keys under scoped encrypted access; signed access JWTs intentionally carry the usage key, never callback URLs or public infrastructure outputs.

Upstream Cognito logout, coordinator browser logout, grant/refresh revocation and already-issued access-token lifetime are distinct. Coordinator logout revokes refresh; existing access JWTs remain valid until expiry. The [authorization contract](authorization.md#denial-and-revocation) defines cancellation, renewal, refresh failure and live host checks; Cognito logout alone does not revoke service JWTs.

## Discovery and host compatibility

Expose public protected-resource metadata with `resource` and `authorization_servers`; its exact URL is advertised in the 401 challenge. Standard well-known resource locations insert `/.well-known/oauth-protected-resource` before the MCP resource path, with a root metadata fallback. These are URL routes, not required physical folders; multiple resource documents may share one authorization server.

Support OAuth authorization-server metadata and OIDC discovery compatibility documents containing exact issuer, authorization/token/JWKS endpoints, code/refresh grant types, S256 and registered-public-client authentication `none`. For issuer `https://host/prefix`, client lookup order is `https://host/.well-known/oauth-authorization-server/prefix`, then `https://host/.well-known/openid-configuration/prefix`, then `https://host/prefix/.well-known/openid-configuration`; root issuers use the corresponding root well-known URLs. Publish consistent documents at reachable configured locations. A named-stage-only API cannot invent origin-root routes: explicitly plan gateway/custom-domain mappings for selected discovery aliases, retain the stage-prefixed OIDC fallback, and report unsupported lookup paths rather than claiming they exist. Verify the complete advertised chain with ChatGPT and Claude before cutover; resolve mapping/domain requirements first if a host cannot use the fallback.

Advertise only implemented capabilities, with exact matching issuer/resource/callback/JWT strings; discovery does not imply OIDC ID-token/userinfo support or dynamic client registration.

Public discovery, `/authorize`, Cognito callback, `/token`, JWKS and browser onboarding endpoints do not require a paid token/native key. This means only the protocol entry point is public: session/token/CSRF validation still protects each operation. CORS is limited to the metadata/authorization surfaces needed by tested clients; no browser MCP transport is added to spec 001.
