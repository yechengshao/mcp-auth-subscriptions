# Contract: AI Client Connection and Paid OAuth Completion

**Status**: Planned, not implemented. Applies to the REST target profile; [Node.js onboarding](onboarding-workflow.md), [authorization](authorization.md), [gateway](rest-gateway.md) and [billing continuation](../../003-billing-subscriptions/contracts/checkout-onboarding.md) define the trust boundaries.

## Browser and client sequence

1. ChatGPT/Claude connect/sign-in/first protected request initiates authorization when the host chooses. Installation alone is not a portable redirect hook. Missing/invalid bearer access receives an upstream 401 with `WWW-Authenticate: Bearer resource_metadata="<advertised HTTPS metadata URL>"`. The resource metadata identifies the exact canonical MCP resource and access-coordinator issuer.
2. The host sends the coordinator `/authorize` a registered client ID, exact redirect URI, state, approved scopes, MCP `resource`, `response_type=code`, S256 challenge and method. Validate before any redirect. Persist a bounded DynamoDB transaction and respond promptly with the login redirect. The browser sees only an opaque reference; progress survives Lambda restarts. Initial clients are explicitly registered with `token_endpoint_auth_method=none`; do not advertise CIMD, DCR, private_key_jwt or OIDC userinfo until implemented and tested. Exact ChatGPT callback/client configuration comes from its management page; Claude configuration is independent.
3. The coordinator redirects to Cognito identity verification using its own upstream authorization-code/S256 transaction. Its Cognito callback is distinct from the AI-client callback. Validate upstream state/nonce/PKCE and Cognito tokens, then durably bind immutable Cognito issuer/subject to the pending downstream transaction and conditionally advance its persisted onboarding state using current entitlement. Never pass an upstream Cognito code to the AI host.
4. With a trusted bounded identity continuation, read current entitlement; this is not successful application login. Eligible users with a ready metering binding skip purchase. Others see spec 003's approved plan selection, order and Stripe-hosted Checkout through the billing-owned flow. The coordinator supplies identity via a scoped internal IAM call, not a browser-supplied subject or a paid MCP bearer. Purchase/status actions return via the coordinator with browser CSRF protection; management operations enforce [FR-004](../spec.md#functional-requirements). Stripe sees only the billing order's scoped identifiers, not OAuth state/PKCE or client credentials.
5. Browser Checkout return displays pending/success/cancelled state through short status requests. Billing commits a verified activation outbox before the access event handler advances matching transactions; a browser return cannot establish payment. Transition logic and resume endpoint require server-side verification: committed current billing entitlement plus matching ready subscriber usage-plan binding. Payment-confirmed-but-binding-pending remains activation pending; no access code/token yet. Bounded status checks/retry permit API Gateway key-association propagation. Stripe redirect parameters are never payment authority.
6. After a conditional transition marks OAuth completion ready and the browser resume endpoint confirms the transaction is still valid, return a short-lived one-use code, original state and exact issuer `iss` to the registered AI callback. Errors to a previously validated redirect include state and matching issuer too. An invalid/unregistered redirect is a local error, never a redirect. No access/refresh token, usage key or subscription record enters the callback URL.
7. At `/token`, verify the code atomically once, client, exact redirect, original S256 verifier and resource. Recheck entitlement and ready binding before issuing access/refresh tokens in a noncacheable JSON response. The host stores them and sends `Authorization: Bearer <access_token>` on subsequent MCP requests. The resource audience matches the canonical `/mcp` URL exactly.
8. Refresh rotates the opaque refresh credential, checks grant/client/resource binding and current paid entitlement/binding, rejects replay and enforces grant expiry/revocation. Eligible reconnect and refresh never create new Stripe orders. Unpaid users may reopen only purchase/renewal enrollment; paid application login, refresh and billing management remain denied.

## Durable state and bounds

The [Node.js onboarding contract](onboarding-workflow.md) implements these phases with conditional DynamoDB writes, durable work, event handlers and scheduled recovery; browser/session and code/grant storage remain authoritative across retries. No gateway request or Lambda worker remains open for the waiting phases.

States: `authorization_pending → identity_verified → checkout_pending → payment_pending → activation_pending → code_ready → code_redeemed`; existing subscribers may skip checkout. Cancelled/expired/denied states cannot mint codes. Payment may finish after the OAuth transaction expires: preserve the paid subscription, require fresh authorization and reuse that entitlement instead of charging again.

Technical defaults to implement and test: authorization continuation 30 minutes absolute, authorization code 60 seconds one-use, service access TTL 5 minutes, refresh grant 24 hours absolute with rotation. Browser sessions are bounded to the onboarding transaction and use Secure/HttpOnly/SameSite cookies, login-session rotation and anti-CSRF for mutations. Expiry is checked on every use; DynamoDB TTL deletion is only housekeeping. Concurrent/replayed transitions use conditional/transactional writes. Store digests of codes/refresh credentials, not their raw values; exclude state, codes, cookies and verifiers from logs. Binding records contain the internal native key value only under scoped encrypted storage/read access, never in grants/public outputs.

Upstream Cognito logout, coordinator browser logout, grant/refresh revocation and already-issued access-token lifetime are distinct. Revoke the grant on coordinator logout; the authorizer checks current grant revocation on each request along with entitlement and binding, so committed local revocation is enforced on the next decision. Upstream Cognito logout alone is not a promise of immediate downstream revocation. Bound signing-key cache behavior separately from uncached grant/entitlement reads.

## Discovery and host compatibility

Expose protected-resource metadata at an explicit advertised HTTPS URL. Use a path-based coordinator issuer compatible with the named REST stage, with its OIDC discovery document at `<issuer>/.well-known/openid-configuration`; advertise only OAuth scopes/capabilities actually implemented. No OIDC identity scopes or ID-token/userinfo capability is implied by using that discovery format. Issuer strings match exactly in discovery, resource metadata, callbacks and service JWTs. Authorization-server discovery must be checked against both real hosts, including path issuers. Do not invent a root-domain well-known route that a stage-only API cannot serve; a custom domain is a separate decision if host compatibility requires it.

Public discovery, `/authorize`, Cognito callback, `/token`, JWKS and browser onboarding endpoints do not require a paid token/native key. This means only the protocol entry point is public: session/token/CSRF validation still protects each operation. CORS is limited to the metadata/authorization surfaces needed by tested clients; no browser MCP transport is added to spec 001.
