# Contract: Cognito Identity, Service Tokens and REST Authorizer

**Status**: Planned, not implemented; supersedes the direct-Cognito-bearer/HTTP-authorizer contract. The [client flow](client-onboarding.md) is authoritative for OAuth completion.

## Separate identity and service issuers

Cognito managed login uses a public app client, authorization code + S256 PKCE, no client secret. Create mode retains a pool/client/domain with operator/admin enrollment initially; compatible reuse checks the whole pool/client/domain and callback/scopes configuration without resetting users, taking ownership or changing policies silently. Self-registration and additional client flows need explicit design changes. Cognito callback/logout URLs are exact operator inputs for the coordinator, not guessed AI-host callbacks.

The coordinator validates upstream Cognito signature/algorithm/key/issuer, ID-token audience/nonce and access-token client/type/time/scope as applicable before accepting the login. Only verified immutable Cognito issuer/subject determines billing ownership. Email never establishes ownership. Cognito signing keys and upstream JWT claims are distinct from downstream service signing keys and claims. Application code cannot mint Cognito JWTs or lengthen their expiry.

The coordinator issues its own asymmetric RS256 service JWT with managed nonexportable signing key (planned KMS RSA signing/JWKS), exact issuer and MCP resource audience. Required claims are `iss`, `sub` (access-owned stable identity handle), `aud`, `client_id`, `grant_id`, `scope`, `iat`, `nbf`, `exp`, `jti`, `token_use=access`, `plan_id`, `subscription_valid_until`, and `entitlement_revision`. Grant state binds the handle to upstream issuer/subject, registered client and resource. Do not expose Stripe IDs, raw API keys or full upstream claims. Expiry is the earlier of issuance plus configured five-minute TTL and current entitlement validity; validate ordering/types and limited clock skew (at most 30 seconds, never extend the subscription bound). Only `/token` returns bearer/refresh credentials; callbacks return codes.

Retained access DynamoDB stores hold bounded OAuth transactions, client/grant/revocation state, durable work and subscriber bindings separately from billing projections. Codes/refresh credentials are hashed and atomically consumed/rotated. Coordinator endpoints own session/grant state, selected-key signing and exact billing IAM invocation. Separate event/recovery handlers read the scoped billing outbox/stream and conditionally advance access state; only the native-key worker manages keys/plans. The [onboarding contract](onboarding-workflow.md) defines leases, current-state checks, deadlines and recovery. Access has no billing writes or Stripe credentials. Explicitly minimize API Gateway management actions/resource scopes; key operations are not all API-ID scoped.

## REQUEST authorizer

A separately packaged Node.js/ARM64 Lambda uses isolated npm-locked JWT and AWS SDK for JavaScript v3 DynamoDB dependencies, with a direct REQUEST handler rather than Express routing. REST REQUEST events use `methodArn`, not HTTP API payload-2.0 `routeArn`. Validate exact expected account/region/API/named stage, allowed method/path, one bounded well-formed Bearer header, RS256/kid, service issuer/audience/client/type/scope, times and trusted JWKS. Never fetch token-supplied key URLs. JWKS cache is bounded to 300 seconds, fetch to three seconds and one unknown-kid refresh with bounded negative caching; unavailable trustworthy keys fail closed.

Before allowing paid MCP or public health, use current strongly consistent base-table reads of grant/revocation state, [billing entitlement](../../003-billing-subscriptions/contracts/entitlements.md) and subscriber binding. Require matching identity/client/resource, unrevoked grant, `allowed=true`, a future `valid_until`, recognized plan and committed revision, and an enabled ready binding for that current plan/stage. A token's plan/revision is an observation; it never overrides current records. Plan/revision changes require a newly refreshed credential if token observations disagree; deny stale credentials rather than selecting an old key. Missing, malformed, stale, denied, expired or unavailable input denies before MCP; no Stripe calls or billing-policy computation.

Return `principalId`, an IAM `policyDocument` scoped to the exact allowed request method ARN, minimal nonpersonal context, and top-level `usageIdentifierKey` equal to that subscriber's current native key value. No wildcard Allow and no key in context/logs/client response. Configure REST identity source `method.request.header.Authorization`, TTL 0, API `ApiKeySourceType=AUTHORIZER`, paid methods `AuthorizationType=CUSTOM` and `ApiKeyRequired=true`. No payload-format/simple-response fields belong on this REST authorizer. Gateway owns exact authorizer-alias invocation permission with SourceAccount.

The authorizer role has only its scoped log writes and read-only grant/entitlement/binding access. It cannot sign tokens, manage keys/plans, write billing/access state, call Stripe or read MCP provider credentials. The service role remains log-only. Authorizer and refresh decisions remain synchronous and never depend on event/recovery completion. Identity verification can establish only the purchase-only continuation defined in [FR-004](../spec.md#functional-requirements); application login and management require current paid eligibility. Coordinator and billing handlers check this on each management operation, including existing sessions/links.

## Denial and revocation

Missing/bad credentials produce an upstream 401 with the correct resource-metadata challenge via REST GatewayResponses; valid-but-ineligible requests return 403. Unexpected infrastructure/authorizer errors are diagnosed separately and never counted as evidence of correct credential rejection. No access-decision/grant/entitlement cache initially. Commit-local grant revocation and paid entitlement transitions affect the next decision; unobserved upstream identity/provider changes remain bounded by documented delivery/session/token rules.

The MCP process validates no JWT and requires no OAuth, DynamoDB, Stripe or signing SDK/environment/IAM grant. Its internal `/health` remains independent.
