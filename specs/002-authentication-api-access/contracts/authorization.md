# Contract: Cognito Identity, Service Tokens and REST Authorizer

**Status**: Planned, not implemented; supersedes the direct-Cognito-bearer/HTTP-authorizer contract. The [client flow](client-onboarding.md) is authoritative for OAuth completion.

## Separate identity and service issuers

Cognito managed login uses a public app client, authorization code + S256 PKCE, no client secret. Create mode retains a pool/client/domain with operator/admin enrollment initially; compatible reuse checks the whole pool/client/domain and callback/scopes configuration without resetting users, taking ownership or changing policies silently. Self-registration and additional client flows need explicit design changes. Cognito callback/logout URLs are exact operator inputs for the coordinator, not guessed AI-host callbacks.

The coordinator validates upstream Cognito signature/algorithm/key/issuer, ID-token audience/nonce and access-token client/type/time/scope as applicable before accepting the login. Only verified immutable Cognito issuer/subject determines billing ownership. Email never establishes ownership. Cognito signing keys and upstream JWT claims are distinct from downstream service signing keys and claims. Application code cannot mint Cognito JWTs or lengthen their expiry.

The coordinator issues its own asymmetric RS256 service JWT signed locally using an RSA private key stored as a Parameter Store SecureString, exact issuer and MCP resource audience. Required claims are `iss`, `sub` (access-owned stable identity handle), `aud`, `client_id`, `grant_id`, `scope`, `iat`, `nbf`, `exp`, `jti`, `token_use=access`, `plan_id`, `subscription_valid_until`, and `entitlement_revision`, and nonempty string `usageIdentifierKey` (the native subscriber key value). Grant state binds the handle to upstream issuer/subject, registered client and resource. The signed payload intentionally exposes the usage key to the token holder; changing it invalidates the signature. Do not expose Stripe IDs or full upstream claims, or log/export tokens or keys. Configure AUTHORIZER key source so the visible key alone cannot bypass bearer authorization. Expiry is the earlier of issuance plus one-hour TTL and current entitlement validity; validate ordering/types and limited clock skew (at most 30 seconds, never extend the subscription bound). Only `/token` returns bearer/refresh credentials; callbacks return codes.

Retained access DynamoDB stores hold bounded OAuth transactions, client/grant/revocation state, durable work and subscriber bindings separately from billing projections. Codes/refresh credentials are hashed and atomically consumed/rotated. Coordinator endpoints own session/grant state, selected-key signing and exact billing IAM invocation. The same access Lambda performs bounded provisioning during onboarding HTTP requests; it has no queue or replay handler, and token routes only issue credentials after current readiness. The [onboarding contract](onboarding-workflow.md) defines leases, current-state checks, deadlines and recovery. Access has no billing writes or Stripe credentials. Explicitly minimize API Gateway management actions/resource scopes; key operations are not all API-ID scoped.

Access record keys, digests, replay tombstones and atomic code/refresh transactions follow [access storage](access-storage.md).

## Signing-key storage, cache and rotation

Store an operator-generated RSA private signing key as a Parameter Store SecureString, supplied through a secure provisioning path outside source, images, CloudFormation plaintext parameters/outputs, logs and evidence. Configure only its exact parameter ARN/version and public `kid` in the coordinator; never accept key locations from requests. Retrieve using AWS SDK `GetParameter` with decryption and sign RS256 locally with a maintained JWT library. SecureString still uses KMS encryption at rest; there is no KMS `Sign` call per token.

Cache the validated parsed private key only in each Lambda execution environment's memory, never disk or application DynamoDB. Cold starts retrieve it; warm invocations reuse it with a bounded maximum cache age of 300 seconds, then re-fetch the configured version. Deduplicate concurrent fetches; retrieval timeout is three seconds. Missing, malformed, mismatched or inaccessible keys fail issuance closed without credentials; a failed refresh of an expired cache does not permit indefinite stale-key use. Parameter Store/key-service outages do not stop verification of already-issued JWTs against trusted public keys.

The coordinator alone receives exact-parameter `ssm:GetParameter`; grant narrowly scoped `kms:Decrypt` only as required by the selected SecureString encryption key and parameter context. No signing-key read/decryption grants for authorizer, MCP or billing; HTTP token/provisioning handlers share the access function role, so private-key isolation is not claimed between them. Public JWKS publishing must use a separately supplied public-key artifact, so a public-key route does not need private-key access. The coordinator's existing signing capability now means local key use, not KMS signing permission.

Rotation publishes the new public key before switching the configured private-key version/`kid`; pin compatible pairs and verify their match before issuance. Roll or refresh all signer instances and record the last possible old-key issuance, accounting for cache and deployment overlap. Retain old public keys for at least the maximum access lifetime plus permitted clock skew after that point. Rollback must preserve verifiability of all unexpired tokens. Test cold/warm cache behavior, concurrent retrieval, cache expiry/outage, denied IAM, malformed keys, key/version mismatch and overlapping rotation/rollback; no real secret values enter fixtures or reports.

## REQUEST authorizer

A separately packaged TypeScript/Node.js ARM64 Lambda uses isolated npm-locked JWT dependencies, with a direct REQUEST handler rather than Express routing. REST REQUEST events use `methodArn`, not HTTP API payload-2.0 `routeArn`. Validate exact expected account/region/API/named stage, allowed method/path, one bounded well-formed Bearer header, RS256/kid, service issuer/audience/client/type/scope, times and trusted JWKS. Never fetch token-supplied key URLs. JWKS cache is bounded to 300 seconds, fetch to three seconds and one unknown-kid refresh with bounded negative caching; unavailable trustworthy keys fail closed.

Before token issuance and every refresh, the coordinator uses current strongly consistent grant/revocation, [billing entitlement](../../003-billing-subscriptions/contracts/entitlements.md) and subscriber-binding reads: matching identity/client/resource, unrevoked grant, allowed future entitlement, recognized current plan/revision and enabled ready stage binding. Unavailable or mismatched state blocks issuance. The authorizer performs no datastore/subscription/binding lookup; require valid signed claims, a nonempty string `usageIdentifierKey`, `exp <= iat + 3600` and `exp <= subscription_valid_until`. Missing, malformed, tampered or expired tokens deny before MCP. Signed plan/revision claims are issuance snapshots, not current-state guarantees.

Return `principalId`, an IAM `policyDocument` scoped to the exact allowed request method ARN, minimal nonpersonal context, and top-level `usageIdentifierKey` equal to the validated token's `usageIdentifierKey` claim. No wildcard Allow and no key in context/logs; return the key only to API Gateway, not an injected header. Configure REST identity source `method.request.header.Authorization`, TTL 0, API `ApiKeySourceType=AUTHORIZER`, paid methods `AuthorizationType=CUSTOM` and `ApiKeyRequired=true`. No payload-format/simple-response fields belong on this REST authorizer. Gateway owns exact authorizer-alias invocation permission with SourceAccount.

The authorizer role has only scoped log writes, required X-Ray telemetry export and trusted JWKS retrieval, with no DynamoDB access. It cannot sign tokens, manage keys/plans, write billing/access state, call Stripe or read MCP provider credentials. The service role remains log-only. Token validation and refresh decisions remain synchronous; refresh requires current readiness. Identity verification can establish only the purchase-only continuation defined in [FR-004](../spec.md#functional-requirements); application login and management require current paid eligibility. Coordinator and billing handlers check this on each management operation, including existing sessions/links.

## Token and revocation requests

`POST /token` accepts `application/x-www-form-urlencoded` and dispatches on `grant_type`. `authorization_code` requires code, registered `client_id`, exact `redirect_uri`, original `code_verifier` and bound MCP `resource`; atomically consume the code and recheck current authority. `refresh_token` requires the opaque credential and registered client binding; any supplied resource/scope must match or narrow the stored grant, never expand it. Neither exchange accepts browser identity or Cognito tokens as a substitute. Missing/unsupported grant types and invalid code/refresh inputs return appropriate OAuth errors without credentials. Return tokens as JSON directly to the AI backend, never a redirect; use `Cache-Control: no-store` and `Pragma: no-cache`.

`POST /revoke` accepts a form-encoded refresh `token`, registered `client_id` and optional `token_type_hint=refresh_token`; public clients have no fabricated shared secret. Validate the token's stored client ownership and revoke its family; unknown or already revoked tokens return RFC 7009 non-disclosing success. This does not invalidate locally verified access JWTs or revoke Cognito tokens. Browser logout uses the separate session/CSRF operation in the [endpoint contract](endpoints.md).

## Denial and revocation

Missing/bad credentials produce an upstream 401 with the correct resource-metadata challenge via REST GatewayResponses; valid tokens lacking the required route scope return 403. Unexpected infrastructure/authorizer errors are diagnosed separately and never counted as evidence of correct credential rejection. Authorizer decision caching is disabled. Opaque hashed refresh credentials rotate atomically and expire at the subscription expiry recorded at initial issuance; rotation cannot extend that deadline. Renewal requires a fresh authorization grant to acquire a later refresh deadline. Revoking a grant/refresh family, or ending paid eligibility, blocks subsequent refresh with OAuth `invalid_grant`; unavailable state returns a retryable error without tokens. Logout also revokes refresh. Already-issued access tokens remain valid until `exp`, at most 1 hour after issuance. Cognito logout/revocation does not invalidate locally verified service JWTs. No automatic renewal occurs; expired users must explicitly purchase a new term through onboarding. Current-term cancellation is support-assisted under billing policy; immediate eligibility revocation disables refresh but does not immediately invalidate access JWTs. Token responses include `access_token`, `token_type=Bearer`, remaining `expires_in`, and rotated `refresh_token`, with no-store headers. ChatGPT/Claude refresh and reconnect behavior must be verified live; a failed refresh requires reauthorization, not a guaranteed automatic login prompt, and ineligible re-login is denied.

The MCP process validates no JWT and requires no OAuth, DynamoDB, Stripe or signing SDK/environment/IAM grant. Its internal `/health` remains independent.
